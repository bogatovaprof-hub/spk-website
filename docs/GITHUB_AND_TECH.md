# GitHub, сборка и публикация прототипа

## Что означает «сначала на GitHub»

В репозитории храним исходный код и версии. GitHub Pages можно использовать для просмотра статической сборки. Это разные действия: загрузка кода не означает автоматически опубликованный сайт. В этом комплекте репозиторий не создавался и публикация не выполнялась.

GitHub Pages обслуживает статические HTML/CSS/JS-файлы. Для этой итерации это подходит: серверная обработка заявок не входит в прототип. Реальный backend для форм и загрузки файлов будет отдельной задачей.

Официальные источники, просмотренные 10.09.2026:

- Astro → Deploy to GitHub Pages: https://docs.astro.build/en/guides/deploy/github/
- Astro → Install: https://docs.astro.build/en/install-and-setup/
- GitHub → What is GitHub Pages: https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages
- GitHub → Securing Pages with HTTPS: https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https

## Безопасный порядок действий

1. Пользователь выбирает существующий или создаёт новый репозиторий и подключает его к своей среде Codex. Имя-ориентир `spk-website`; это предложение, не уже существующий репозиторий.
2. Содержимое папки `spk_codex_kit` помещается в рабочую папку репозитория. В существующем проекте сначала проверить конфликты; не копировать `.gitignore` и `AGENTS.md` поверх чужих файлов без объединения правил.
3. Codex создаёт отдельную ветку, сохраняет исходные материалы, реализует проект, фиксирует зависимости и тестирует.
4. После проверки пользователь или Codex с необходимыми правами включает Pages → Source: GitHub Actions. Не менять видимость репозитория автоматически.
5. Workflow для первой публикации запускается вручную. Автоматический deploy после каждого изменения main можно добавить позже.
6. После успешного job `deploy` открыть фактический адрес результата, проверить главную, страницу услуги, форму и вложенные ресурсы. Отдельно выполнить refresh на внутренней странице.

## Особенность подпапки

Для проектного репозитория адрес имеет вид `https://OWNER.github.io/REPO/`. Поэтому ссылка `/services/` без префикса может вести не в этот проект. Нужно централизованно учитывать `base` и для страниц, и для картинок, и для иконок, и для favicon.

В `examples/astro.config.example.mjs` показан принцип вычисления `site`/`base`; это не автоматически готовая конфигурация. В `examples/urls.example.ts` — локальный helper. Не передавать helper уже префиксованные пути.

Для репозитория `OWNER.github.io` base равен `/`. Для будущего отдельного домена тоже обычно `/`, но домен сейчас не подключаем. Если у организации особый URL Pages, явно задавать SITE_ORIGIN/SITE_BASE вместо предположения.

В CSS не оставлять абсолютный `url('/images/...')`: в подпапке он сломается. Передавать корректный URL из компонента через style/custom property или использовать импорт ресурсов, обработанный сборкой. Проверить image sources, links, canonical, Open Graph, favicon и страницу 404.

## Node и зависимости

Предлагаемый ориентир — Node 24, стабильный Astro, TypeScript, `@astrojs/check`, Playwright для smoke-проверок, `@fontsource-variable/roboto` для рабочего шрифта. Выбирать только фактически совместимые версии, зафиксировать lockfile и версию Node.

Не устанавливать «всё сразу» без необходимости. React/Tailwind/shadcn не являются требованием. Здесь важнее точность собственного CSS, чем скорость на универсальном шаблоне.

Точный номер Astro намеренно не зафиксирован в задании: его должен определить разработчик при реальной установке и записать в package.json/lockfile. То же относится к версиям Actions. Пример workflow отражает просмотренную официальную инструкцию, но в этой среде не запускался.

## Что не должно попасть в публичный репозиторий

Пароли, токены, `.env` с секретами, доступы почты и регистратора, реальные обращения, загруженные чертежи, договоры и файлы клиентов. Бинарные системные шрифты из контейнера не копировать. Подключение шрифта — через выбранный пакет и его исходную лицензию в процессе разработки.

Исходный `СПК сайт.docx` в пакет не скопирован: для разработки достаточно выделенных текстов и решений. В публичную сборку `dist` не должны попасть `reference`, `docs`, `qa`, исходные клиентские материалы и тестовые файлы.

## Публичность и индексация

Обычный Pages-сайт доступен в интернете; закрытый репозиторий сам по себе не означает закрытый опубликованный сайт. Фактическая доступность зависит от настроек и плана организации, её надо проверить.

`noindex` — инструкция поисковым роботам, не пароль и не контроль доступа. Для прототипа установить meta noindex на всех страницах; не публиковать конфиденциальное содержимое в расчёте на этот meta-тег.

Google отдельно указывает: робот должен иметь возможность прочитать страницу с noindex. Поэтому не закрывать все эти страницы в robots.txt одновременно. Кроме того, robots.txt применяется на уровне корня сайта, а не произвольной подпапки проекта. Источник: https://developers.google.com/search/docs/crawling-indexing/block-indexing

## Формы

На Pages не подключаем серверные endpoints Astro и не притворяемся, что `fetch('/api/contact')` работает. Формы только локально валидируют ввод и выбор файлов. Позднее можно выбрать отдельный обработчик, хостинг с backend или другую архитектуру; сейчас выбор не делается.

## Корпоративная почта и домен — отдельный этап

В документе клиента указан `spk-traid.ru`; на утверждённой картинке `info@spk-trade.ru`. Не считать это одним и тем же адресом. В настройках прототипа сохранены оба источника и пометка конфликта.

Запрос о пяти почтовых адресах с расширением до пятнадцати зафиксирован в backlog. GitHub Pages не используется как почтовый сервер. Не создавать DNS-записи, почтовые ящики и CNAME этой итерацией.

## Финальный статус

В отчёте должны отдельно стоять:

- код создан / не создан;
- локальная сборка прошла / не прошла;
- тесты пройдены / не выполнены;
- изменения отправлены в ветку / не отправлены;
- Pages опубликован / не опубликован;
- фактический URL или точный оставшийся шаг.

Не заменять эту проверку фразой «готово, всё должно работать».
