# Задание Codex: многостраничный прототип сайта СПК ТРЕЙД

**Версия 1.0 · 10 сентября 2026 года**

## 0. Результат, который нужно сделать

Реализовать рабочий адаптивный многостраничный сайт на основе утверждённого светлого референса. Результат — исходный код в GitHub-репозитории, локальная сборка, навигация между страницами, работающие интерфейсные состояния форм, тесты и возможность показать статический прототип через GitHub Pages.

Это задача **реализации**, а не повторного анализа концепции. Не останавливаться после плана или структуры файлов. Сначала коротко сообщить этапы, затем создать страницы, стили, поведение и тесты. Отсутствие рабочих контактов и подробных материалов АПК/частного строительства не блокирует прототип: правила заполнения заданы ниже.

У пользователя уже утверждены композиция и стилистика. Не проводить новый творческий поиск и не подменять результат готовым шаблоном строительного сайта.

**Текущий выданный пакет — задание, данные и изображения. Это ещё не приложение, у него пока нет работающей Astro-сборки.** Не сообщать, что сайт был собран, пока это действительно не выполнено в среде Codex.

## 1. Приоритет источников

1. Последующее прямое указание пользователя, если оно относится к конкретной правке.
2. `reference/home-approved.png` — утверждённый внешний вид главной.
3. `src/data/home.json` — зафиксированный текст главной, переписанный из изображения.
4. `src/data/services.json`, `about.json`, `faq.json`, `objects.json`, `forms.json` — текст клиента для дополнительных страниц.
5. `docs/DESIGN_SYSTEM.md` и `src/styles/tokens.css` — предложенная реконструкция параметров оформления.
6. `src/data/pages.json` — нейтральные тексты новых служебных состояний и коротких шаблонов.

Не брать тексты и фотографии из старых тёмных макетов. Не смешивать названия и преимущества из других концепций. Не улучшать рекламные формулировки по собственной инициативе.

В исходном документе было десять услуг. В финальном изображении восемь карточек: два типа полов объединены, гидроизоляция не вынесена. Решение для v1: **главная — восемь карточек, каталог — все десять услуг**. Не возвращать десять карточек на главную без отдельной команды.

## 2. Технический подход

Для нового репозитория использовать **Astro + TypeScript + обычный CSS с переменными**, статический вывод. React, Next.js, CMS, база данных, серверная авторизация и большие UI-библиотеки для этой задачи не требуются. Выбор Astro — предложенное техническое решение для прототипа, а не требование клиента из исходного документа.

Если в выбранном репозитории уже есть рабочее приложение — сначала прочитать его README, AGENTS и package.json. Не перезаписывать существующую работу. Совместимый готовый стек можно сохранить с фиксацией решения; не проводить миграцию молча.

Перед установкой проверить актуальную стабильную версию Astro и совместимую чётную версию Node. Рабочий ориентир — Node 24, но версия должна соответствовать фактическому окружению и документации. Не устанавливать prerelease. Зафиксировать Node, зависимости и lockfile; не оставлять зависимость `latest` в коммитах.

Вывод `static`, конечные адреса с завершающим `/`, реальная HTML-страница для каждого маршрута. Не использовать SPA-router с имитацией страниц и fallback всех адресов на index.html. Все ссылки и изображения обязаны работать как в корне, так и в подпапке GitHub Pages.

Рекомендуемые команды проекта после реализации:

- `npm run dev` — локальная разработка;
- `npm run check` — проверка Astro/TypeScript;
- `npm run build` — статическая сборка;
- `npm run preview` — просмотр результата сборки;
- `npm run test:smoke` — проверка маршрутов, форм и основных взаимодействий;
- `npm run test:pages-base` — проверка сборки с тестовым base path;
- `npm run test:a11y` — автоматические проверки доступности, если библиотека доступна.

Не создавать фиктивные команды, которые завершаются успешно, ничего не проверяя.

## 4. Главная: точная последовательность

Главная состоит из **семи визуальных зон**:

1. Шапка.
2. Первый экран.
3. Четыре факта.
4. Восемь карточек услуг.
5. Панель «Обсудим ваш проект?».
6. Две карточки специальных направлений.
7. Подвал.

Не вставлять на главную дополнительные длинные блоки «О компании», «Этапы», «FAQ», «Отзывы», «Проекты» и «Наши клиенты». Для существующих пунктов меню есть отдельные страницы. Главная должна остаться такой же компактной по логике, как референс.

### 4.1. Шапка и навигация

Меню и кнопка берутся из `site.json`. Переход по логотипу — на `/`. Активный пункт выделен синим. Подразделы услуг активируют «Услуги». В header не добавлять выпадающее мегаменю на полэкрана.

Мобильное меню доступно клавиатурой, имеет `aria-expanded` и `aria-controls`, закрывается по Escape, по выбору ссылки и кнопкой. Если используется modal-поведение — управлять фокусом и блокировкой прокрутки. После закрытия возвращать фокус на кнопку меню.

### 4.2. Первый экран

Весь текст строго из `home.hero`. Справа `hero-industrial-right`, слева CSS-подложка. Сам hero — отдельный компонент, текстовые переносы управляемые, но не встроенные в фото. Декоративный фон не должен получать lazy loading. Зарезервировать размер, чтобы не было скачка вёрстки.

«Отправить проект на расчет» ведёт на `/request/`.
«Обсудить задачу» открывает диалог консультации, тот же на всех страницах.

### 4.3. Факты

Текст не заменять на «более 35», «20+», «опыт 35 лет команды» и другие трактовки. На главной показывать буквально значения и подписи из `home.facts`. Вопросы подтверждения вынесены в служебный backlog, не нужно обвешивать главную юридическими оговорками.

### 4.4. Услуги

Карточки — данные `home.cards`, порядок неизменный. «Все услуги» ведёт на `/services/`. Карточка объединённых полов ведёт на страницу бетонных полов, где в верхней части есть понятная ссылка «Полимерные полы». На каталоге отдельно доступны оба вида полов и гидроизоляция.

### 4.5. Форма на главной

Заголовок, описание, поля, кнопка и преимущества — `home.lead`. Не заменять этот текст на более длинный текст расширенной формы клиента: он используется на `/request/`.

Визуал из референса, семантика формы живая. Не использовать сохранённый `section-lead.png` как фон с уже нарисованными полями — это только контрольный снимок.

### 4.6. Специальные направления

Две карточки — данные `home.directions`. Переходят на два отдельных URL, не раскрывают текст в модальном окне. Не размещать на главной детальные каталоги домов или сельскохозяйственных комплексов.

### 4.7. Подвал

Текстовые контакты из референса сохранить для визуальной сверки. `phoneHref` и `emailHref` сейчас `null`: не создавать `tel:` и `mailto:` для непроверенных заглушек. Политика и карта сайта ведут на существующие страницы. Не добавлять фиктивный ИНН, адрес, год основания и карту офиса.

## 5. Содержимое внутренних страниц

### 5.1. Все услуги

H1 «Услуги». Короткое вводное предложение — из `pages.services`. Сетка всех десяти услуг. Для каждой — название, исходный абзац или его первое предложение без искажения, небольшое изображение при наличии и ссылка на детальную страницу.

Для гидроизоляции — полноценная текстовая карточка без фотографии. Она не должна выглядеть сломанным `<img>`; не показывать «image not found» и не подставлять фотографию монтажа оборудования.

### 5.2. Детальная услуга

Один общий шаблон `ServiceDetail`:

- Breadcrumb: Главная → Услуги → Название.
- H1 из соответствующей записи.
- Полный исходный абзац, не новый SEO-текст.
- Компактная исходная фотография, если есть; не полноэкранный размытый hero.
- Две CTA: «Отправить проект на расчет» и «Обсудить задачу».
- Блок подготовки расчёта — текст из расширенной формы клиента.
- Не более двух-трёх подходящих вопросов из общего FAQ.
- Ссылки на связанные услуги, подобранные из имеющегося списка.

Для промышленного строительства дополнительно вывести весь список `objects.json` с заголовком «Какие объекты мы строим?». Это список областей работ из текста клиента, не портфолио.

На бетонных полах показать блок-ссылку на полимерные покрытия. На полимерных — обратную ссылку. Ниже может быть соответствующий исходный абзац, но не дублировать весь каталог.

Для монтажа оборудования можно показать предоставленное предложение об организации изготовления, поставки и монтажа по ТЗ из `about.json`, не выдумывая производителей и страны.

На страницах оборудования и сэндвич-панелей сохранять формулировки поставки из документа. Не добавлять условия оплаты, монтажные сроки и конкретные марки материалов.

### 5.3. Индивидуальное строительство и АПК

Два компактных законченных в навигационном смысле шаблона. Общая шапка и подвал, breadcrumb, заголовок и подпись именно из утверждённого референса, небольшая фотография соответствующего направления, блок «Обсудим ваш проект?» и форма.

Детальные тексты не предоставлены. Отсутствие контента не маскировать выдуманными проектами, ценами и обещаниями. Использовать только короткий нейтральный текст из `pages.json`; технический статус недостающих материалов фиксировать в отчёте, не обязательно добавлять большую заглушку к первому экрану.

В v1 эти страницы могут быть короткими. Не брать расширенные ИИ-тексты и фотографии из старых изображений в этой беседе.

### 5.4. О компании

Использовать `about.json`: вводное описание, основания и преимущества, абзацы о работе, предложение о консультации. Цифры исходника сохраняются как клиентские утверждения. Никаких самостоятельно придуманных имён, должностей, состава команды и истории по годам.

Фотографию `team-engineers` использовать как иллюстрацию, но не подписывать «наши инженеры Иван и Сергей». Блок «Команда» с персональными карточками не делать.

### 5.5. Проекты

Подготовить масштабируемую структуру `ProjectCard`, но массив реальных проектов оставить пустым. На странице — аккуратное empty state из `pages.projects`. Иллюстрации из референса нельзя выдать за выполненные СПК ТРЕЙД объекты.

Не создавать фиктивные записи с названиями заводов, адресами, бюджетами, площадями и сроками. Не создавать отдельные URL фиктивных проектов. При этом пункт меню «Проекты» должен вести на работающую страницу, а не быть неактивным.

### 5.6. FAQ

Все шесть вопросов и ответов из `faq.json`. Нативный `<details><summary>` допустим и предпочтителен по простоте; добавить понятный indicator. Текст доступен в исходном HTML, не загружается только после клика. Не переписывать ответы о гарантиях и действующем предприятии.

### 5.7. Контакты

Название компании, отображаемые номер и e-mail, аккуратная пометка прототипа о неподтверждённых контактах, кнопка и форма. Адрес, часы работы и реквизиты отсутствуют — не придумывать и не вставлять Google/Yandex-карту произвольного офиса.

### 5.8. Политика, карта сайта и 404

Политика — только корректно названная служебная заглушка. Не писать юридический документ от имени компании без данных оператора.
Карта сайта — реальные маршруты без 404 и без дублей; разбивка на Основные разделы / Услуги / Служебные страницы.
404 — правильный статус на хостинге, понятный H1, кнопка на главную с учётом base path. Не использовать 404 как универсальный SPA-редирект.

## 6. Работа с картинками

Сначала прочитать `docs/ASSETS_GUIDE.md` и `docs/assets-manifest.json`.

Все выданные PNG и WebP — прямые кропы референса. Полные фотографии в высоком разрешении не предоставлены. Не скачивать «похожие», не использовать стоки и не генерировать новые. Не растягивать картинки через `image-rendering: pixelated` и не скрывать дефекты чрезмерной резкостью.

Предпочитать lossless WebP, PNG — fallback или вариант для сравнения. Нельзя повторно сильно сжимать эти маленькие изображения. Не создавать 2x/3x варианты путём увеличения и не выдавать их за повышенное разрешение.

Изображения подключать через единый data/helper mapping, а не копировать пути в десятки компонентов. Для каждого — корректные `width`, `height`, `loading`, `decoding`, alt при необходимости. В hero — eager; ниже первого экрана — lazy. У иллюстраций, которые полностью дублируют соседнее название ссылки, может быть пустой alt.

Контрольные изображения из `reference/` не копировать в `public/` и не включать в публичную сборку. Основной full-page PNG нужен для разработки, но не для показа посетителям.

## 7. Формы и файлы: только честный демонстрационный режим

В первой версии сайт статический. Реальную отправку, CRM, Telegram, SMTP, облачное хранилище и почтовые интеграции **не подключать**. Внешних API-ключей нет и не нужно просить их для завершения визуального прототипа.

Состояния формы: пустая → заполнение → ошибки проверки или успешная локальная проверка. После валидного submit показывать сообщение из `site.ui.demoSubmit`: **«Проверка выполнена. Это прототип: заявка и файлы не отправлены.»**

Запрещены сообщения «Заявка отправлена», «Наш менеджер уже получил заявку» и подобные, если передачи не было. Не имитировать серверную отправку сетевым вызовом на выдуманный URL.

Проверять имя, телефон и, если заполнен, e-mail. Телефон — без жесткой маски только РФ: в исходнике присутствует СНГ. Разрешить `+`, пробелы, скобки и дефисы; разумно проверять количество цифр, не объявлять номер существующим. Ошибки рядом с полем, `aria-invalid`, связь через `aria-describedby`. Сохранять введённые данные в DOM при ошибке.

Поля и обязательность заданы в JSON. Для расширенной формы выбранная услуга может подставляться из безопасного query parameter по разрешённому списку. Не выводить необработанный query string в HTML.

Выбор файла — настоящий `<input type=file multiple>`. Можно показывать имя, размер и кнопку удаления. Не читать содержимое файлов, не сохранять в браузерную БД или localStorage, не отправлять их. Ограничения прототипа: до 10 файлов, до 20 МБ каждый, до 50 МБ суммарно; расширения из `site.formPolicy`. Эти ограничения — настройка демонстрации, а не утверждённые условия компании.

Не записывать введённые телефоны и имена в console.log, тестовые артефакты и URL. Тесты используют только явно тестовые данные, например «Тест» и `+7 000 000-00-00`. В заголовках/снимках тестов не должно быть реальных обращений.

Диалог консультации: фокус внутри при открытии, Escape закрывает, кнопка закрытия доступна, после закрытия фокус возвращается на исходную кнопку. Нативный `<dialog>` допустим; обязательно проверить мобильный вид.

## 9. SEO-подготовка прототипа

Для каждой страницы: `lang="ru"`, осмысленный title, description из исходного текста или краткая нейтральная служебная подпись, один H1, корректная иерархия H2/H3. Общие тексты бренда не должны дублировать H1.

На прототипе в HTML каждой страницы — `<meta name="robots" content="noindex, nofollow">`. Это не защита от доступа и не гарантия полной секретности. Не сочетать noindex с запретом обхода всех страниц через robots.txt, мешающим роботу прочитать meta. В подпапке GitHub Pages нельзя считать локальный `/repo/robots.txt` корневым файлом всего origin.

Canonical, если он выводится, должен указывать на фактический адрес этой сборки, не на ещё не подключённый коммерческий домен. Не создавать canonical всех страниц на `/`. Для preview допустимо не выводить canonical до корректной конфигурации site/base.

HTML-карта сайта нужна для навигации. XML sitemap публичного боевого сайта сейчас не публиковать и в поисковые панели не отправлять. Не подключать Яндекс Метрику, Google Analytics, пиксели, чаты, карты и рекламные счетчики.

Не добавлять структурированные данные с фиктивными рейтингами, адресами, отзывами и датами. Фавикон можно получить из переданного логотипа; не придумывать новый знак.

## 10. GitHub и публикация

Подробности и примеры — `docs/GITHUB_AND_TECH.md` и `examples/`.

Работать в выбранном пользователем репозитории. Ветка `codex/spk-prototype-v1` либо согласованное имя. Сначала проверить `git status` и не затереть незакоммиченные правки. Не переименовывать чужие ветки и не делать force-push.

Создать инструкции запуска и workflow сборки. Не считать успешную локальную сборку успешным деплоем. После публикации отдельно открыть URL и проверить статические ресурсы и вложенные страницы.

Не делать репозиторий публичным без разрешения ради удобства Pages. Не подключать домен, DNS и корпоративную почту в этой итерации. В документе клиента `spk-traid.ru`, а в картинке почта на `spk-trade.ru`: сохранить конфликт в backlog.

GitHub Pages в обычном режиме публичен. Не помещать в публичные материалы реальные ТЗ, документы клиентов, договоры и персональные данные. Шрифт устанавливается через пакет зависимостей в рабочем проекте; контейнерные системные шрифты не копировать в репозиторий.

В пакете workflow приведён как `.example`, чтобы он не включался случайно. Codex должен проверить актуальные версии Actions и создать рабочий `.yml` после настройки. Если прав на настройки Pages нет, завершить код и тесты, а в отчёте точно указать оставшийся шаг пользователя. Не объявлять сайт опубликованным.

# Визуальная система · СПК ТРЕЙД

## 1. Что воспроизводим

Единственный утверждённый визуальный эталон — `reference/home-approved.png`, 1122 × 1402 px. Это светлая версия сайта: бело-голубой фон, почти чёрные тёмно-синие заголовки, насыщенные синие кнопки, реальная по фактуре промышленная иллюстрация, компактные карточки и тонкие контурные иконки. Тёмная версия и другие старые концепции не используются.

Визуальная задача — сверстать этот дизайн живыми компонентами. НЕ ставить картинку сайта на страницу как фон с невидимыми кнопками поверх. Не встраивать подписи карточек, заголовки и формы в изображения. Не предлагать новый дизайн.

Исходный макет — растровая генерация. CSS, точные начертания шрифта, прозрачные исходники и координаты слоёв не предоставлены. Приведённые ниже параметры — инженерная реконструкция, а не извлечение несуществующего Figma-файла.

## 2. Палитра

## 3. Шрифт

Точное название шрифта по PNG установить нельзя. Для первой реализации выбран **Roboto Variable** с кириллицей как визуально близкая рабочая замена. Это не утверждение, что именно он был в генерации.

Установить официальный пакет `@fontsource-variable/roboto`, импортировать `@fontsource-variable/roboto/wght.css`, проверить кириллицу. Семейство: `'Roboto Variable', 'Roboto', Arial, sans-serif`. Шрифт подключать локально через сборку, а не динамическим обращением браузера к Google Fonts. Бинарные файлы шрифтов в выданный пакет не включены.

| Элемент | На ширине около 1122 px | На 1440 px | На телефоне |
|---|---:|---:|---:|
| H1 главной | около 54 px / 800 | до 68 px / 800 | 32–36 px / 800 |
| Подзаголовок hero | около 26 px / 500–600 | до 32 px | 20–22 px |
| H2 секций | 28–30 px / 700 | до 36 px | 26 px |
| H1 внутренних | 36–48 px / 700–800 | до 56 px | 30–34 px |
| Описание в hero | 15–16 px | 18 px | 16 px |
| Основной текст внутренних страниц | 17–18 px | 18 px | 16 px |
| Название карточки | 14 px / 500 | 16 px | 14–16 px |
| Меню | 13–14 px / 500 | 14–15 px | 17 px в раскрытом меню |
| Кнопки | 14–15 px / 500–600 | 16 px | 15–16 px |
| Мелкие подписи | 13 px | 13–14 px | не меньше 13 px |

Для H1 `line-height: 1.02–1.06`, `letter-spacing: -0.025em`. Основной текст `line-height: 1.45–1.55`. Не уменьшать текст ради совпадения общей высоты скриншота. Не использовать трансформации scaleX для искусственного сжатия шрифта.

## 4. Сетка и плотность

Контейнер: `width: calc(100% - 2 * var(--page-gutter)); max-width: 1280px; margin-inline: auto;`.
Горизонтальные отступы `clamp(20px, 5vw, 80px)`. На телефоне 20 px, на узком экране при необходимости 16 px.

Референс — компактная главная, не длинный лендинг с огромными промежутками. Расстояние между соседними секциями 20–32 px. Не назначать всем секциям `padding-block: 100px`.

Шапка 64–80 px; белый слегка прозрачный фон. Не фиксировать её поверх контента в v1: обычное положение в потоке. Логотип примерно 79 × 57 px на эталонной ширине, в реальном header 72–84 px по ширине с сохранением пропорций. Не увеличивать до 150–200 px.

Карточки услуг: на широком экране 4 колонки × 2 строки. На 768–1023 px — 2 колонки. На 480–767 px — 2, когда названия помещаются; ниже 480 px — 1. Все строки имеют одинаковые высоты карточек в пределах ряда. Никаких горизонтальных каруселей услуг в первой версии.

Радиусы: кнопки и поля 6 px; карточки 8 px; крупные панели 12 px. Не использовать большие «пузырьковые» радиусы 24–40 px. Тени очень слабые; границы тонкие.

## 5. Главная, блок за блоком

### Header

Слева логотип, по центру меню из шести пунктов, справа синяя кнопка «Оставить заявку» со стрелкой. Пункты: Главная / Услуги / О нас / Проекты / Вопросы / Контакты. Главная выделена синим и тонким нижним подчёркиванием. На внутренних страницах выделять соответствующий раздел.

При нехватке места переключаться на мобильное меню, а не сжимать подписи до 10 px. Ориентир переключения 1024 px. На телефоне оставить логотип, компактную кнопку «Оставить заявку» и menu-button; если на 360 px тесно — полную CTA перенести в раскрытое меню.

### Hero

Видимая высота в эталоне около 370 px после шапки. Для адаптивной реализации ориентир 380–500 px на компьютере в зависимости от ширины, но `min-height`, не фиксированная высота с обрезанным текстом. На 1122 px допустимо чуть выше оригинала ради читаемости.

Слева текст занимает приблизительно 43–46% внутренней ширины. Справа строительство со стальным каркасом занимает около 57–62% всей секции. Фотография `hero-industrial-right.webp` закреплена справа; её исходная ширина 645 px, высота 369 px. В v1 не растягивать её отдельным полноэкранным баннером на 1920 px. Фоновую левую часть собрать CSS-градиентом белый/очень светлый голубой. На границе с фото — мягкий градиент шириной 60–120 px, не жёсткий разрез.

Текст находится над фоном, но **не поверх тёмных металлоконструкций**. Слой изображения декоративный, `aria-hidden` / `alt=""`, если подпись дублирует смысл. Фото имеет собственные видимые надписи на строительном баннере — не создавать для них новый текстовый блок поверх.

H1 ровно «Промышленное строительство», двумя строками. Затем слоган, затем один абзац, затем две кнопки. Основная синяя, вторичная белая/прозрачная с синей границей. Между кнопками 12–16 px.

На телефоне: текст первым, кнопки столбцом или в две строки без переполнения; ниже отдельное фото с мягким верхним переходом. Не сохранять desktop-текст поверх уменьшенной фотографии. Не использовать `100vh`.

### Полоса фактов

Четыре факта в одну строку, синяя контурная иконка слева, значение жирным, подпись ниже. Вертикальные разделители тонкие. Светлый фон; не делать тёмную полосу и не добавлять цветные квадратные контейнеры к иконкам.

На планшете и телефоне — сетка 2 × 2; высота карточек авто. На 360 px не пытаться уместить четыре факта в одну строку. Текст не меняется.

### Услуги

Заголовок «Наши услуги» слева, «Все услуги →» справа на одной строке. Ровно восемь карточек из `home.json`. Изображение сверху во всю ширину, нижняя светлая область с названием и маленькой стрелкой справа.

Соотношение изображения в эталоне около 2.7:1. Для v1 использовать `aspect-ratio: 2.7 / 1`, `object-fit: cover`, `object-position: center`. На телефоне можно 2.5:1. **Не увеличивать высоту фото до квадратного формата**: это изменит плотность и приведёт к лишнему кадрированию.

Нижняя область 48–60 px / `min-height`; 12–16 px внутренних отступов. Всё содержимое карточки — одна ссылка, без вложенной ссылки-стрелки. Hover: чуть темнее граница, лёгкая тень; не более 2 px подъёма.

### Панель «Обсудим ваш проект?»

## 8. Доступность и поведение

Клавиатурный focus видим на всех интерактивных элементах. Целевой размер управляющих элементов — не менее 44 × 44 px; это выбранное требование к прототипу. Кнопка не должна быть `<div>`. Ссылка — для перехода, `<button>` — для действия.

Проверить контраст текста и элементов. `prefers-reduced-motion` отключает необязательные анимации. Никаких параллаксов, видеофонов, canvas-эффектов, автопрокрутки, загрузочных экранов, фальшивых чат-виджетов и всплывающих скидок.

## 7. Частые вопросы — без изменения смысла

### Можно ли заказать только один вид работ?

Да. Мы рассматриваем как комплексные проекты, так и отдельные задачи: монтаж металлоконструкций, устройство полов, гидроизоляцию, монтаж сэндвич-панелей и другие работы.

### Что необходимо для предварительного расчета?

Желательно предоставить техническое задание, проектную документацию, чертежи или ведомость объемов. Если документов пока нет, можно направить описание задачи и имеющиеся исходные данные.

### Выполняете ли вы проектирование?

Да, компания разрабатывает проектные решения для строительства и отдельных конструктивных элементов. Точный состав проектных работ определяется после изучения задачи.

### Можно ли выполнить работы на действующем предприятии?

Возможность и порядок выполнения определяются после обследования объекта. Учитываются режим работы предприятия, требования безопасности, доступ к рабочим зонам и влияние строительных процессов на производство.

### Как рассчитывается стоимость?

Стоимость зависит от объема и сложности работ, характеристик объекта, применяемых материалов, условий площадки, логистики и сроков реализации.

### Предоставляется ли гарантия?

Гарантийные условия фиксируются в договоре и зависят от вида выполненных работ, примененных материалов и условий эксплуатации.

# GitHub, сборка и публикация прототипа

## Что означает «сначала на GitHub»

В репозитории храним исходный код и версии. GitHub Pages можно использовать для просмотра статической сборки. Это разные действия: загрузка кода не означает автоматически опубликованный сайт. В этом комплекте репозиторий не создавался и публикация не выполнялась.

GitHub Pages обслуживает статические HTML/CSS/JS-файлы. Для этой итерации это подходит: серверная обработка заявок не входит в прототип. Реальный backend для форм и загрузки файлов будет отдельной задачей.

Официальные источники, просмотренные 10.09.2026:

- Astro → Deploy to GitHub Pages: https://docs.astro.build/en/guides/deploy/github/
- Astro → Install: https://docs.astro.build/en/install-and-setup/
- GitHub → What is GitHub Pages: https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages
- GitHub → Securing Pages with HTTPS: https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https

## Безопасный порядок действий

1. Пользователь выбирает существующий или создаёт новый репозиторий и подключает его к своей среде Codex. Имя-ориентир `spk-website`; это предложение, не уже существующий репозиторий.
2. Содержимое папки `spk_codex_kit` помещается в рабочую папку репозитория. В существующем проекте сначала проверить конфликты; не копировать `.gitignore` и `AGENTS.md` поверх чужих файлов без объединения правил.
3. Codex создаёт отдельную ветку, сохраняет исходные материалы, реализует проект, фиксирует зависимости и тестирует.
4. После проверки пользователь или Codex с необходимыми правами включает Pages → Source: GitHub Actions. Не менять видимость репозитория автоматически.
5. Workflow для первой публикации запускается вручную. Автоматический deploy после каждого изменения main можно добавить позже.
6. После успешного job `deploy` открыть фактический адрес результата, проверить главную, страницу услуги, форму и вложенные ресурсы. Отдельно выполнить refresh на внутренней странице.

## Особенность подпапки

Для проектного репозитория адрес имеет вид `https://OWNER.github.io/REPO/`. Поэтому ссылка `/services/` без префикса может вести не в этот проект. Нужно централизованно учитывать `base` и для страниц, и для картинок, и для иконок, и для favicon.

В `examples/astro.config.example.mjs` показан принцип вычисления `site`/`base`; это не автоматически готовая конфигурация. В `examples/urls.example.ts` — локальный helper. Не передавать helper уже префиксованные пути.

Для репозитория `OWNER.github.io` base равен `/`. Для будущего отдельного домена тоже обычно `/`, но домен сейчас не подключаем. Если у организации особый URL Pages, явно задавать SITE_ORIGIN/SITE_BASE вместо предположения.

В CSS не оставлять абсолютный `url('/images/...')`: в подпапке он сломается. Передавать корректный URL из компонента через style/custom property или использовать импорт ресурсов, обработанный сборкой. Проверить image sources, links, canonical, Open Graph, favicon и страницу 404.

## Node и зависимости

Предлагаемый ориентир — Node 24, стабильный Astro, TypeScript, `@astrojs/check`, Playwright для smoke-проверок, `@fontsource-variable/roboto` для рабочего шрифта. Выбирать только фактически совместимые версии, зафиксировать lockfile и версию Node.

Не устанавливать «всё сразу» без необходимости. React/Tailwind/shadcn не являются требованием. Здесь важнее точность собственного CSS, чем скорость на универсальном шаблоне.

Точный номер Astro намеренно не зафиксирован в задании: его должен определить разработчик при реальной установке и записать в package.json/lockfile. То же относится к версиям Actions. Пример workflow отражает просмотренную официальную инструкцию, но в этой среде не запускался.

## Что не должно попасть в публичный репозиторий

Пароли, токены, `.env` с секретами, доступы почты и регистратора, реальные обращения, загруженные чертежи, договоры и файлы клиентов. Бинарные системные шрифты из контейнера не копировать. Подключение шрифта — через выбранный пакет и его исходную лицензию в процессе разработки.

Исходный `СПК сайт.docx` в пакет не скопирован: для разработки достаточно выделенных текстов и решений. В публичную сборку `dist` не должны попасть `reference`, `docs`, `qa`, исходные клиентские материалы и тестовые файлы.

## Публичность и индексация

Обычный Pages-сайт доступен в интернете; закрытый репозиторий сам по себе не означает закрытый опубликованный сайт. Фактическая доступность зависит от настроек и плана организации, её надо проверить.

`noindex` — инструкция поисковым роботам, не пароль и не контроль доступа. Для прототипа установить meta noindex на всех страницах; не публиковать конфиденциальное содержимое в расчёте на этот meta-тег.

Google отдельно указывает: робот должен иметь возможность прочитать страницу с noindex. Поэтому не закрывать все эти страницы в robots.txt одновременно. Кроме того, robots.txt применяется на уровне корня сайта, а не произвольной подпапки проекта. Источник: https://developers.google.com/search/docs/crawling-indexing/block-indexing

## Формы

На Pages не подключаем серверные endpoints Astro и не притворяемся, что `fetch('/api/contact')` работает. Формы только локально валидируют ввод и выбор файлов. Позднее можно выбрать отдельный обработчик, хостинг с backend или другую архитектуру; сейчас выбор не делается.

## Корпоративная почта и домен — отдельный этап

В документе клиента указан `spk-traid.ru`; на утверждённой картинке `info@spk-trade.ru`. Не считать это одним и тем же адресом. В настройках прототипа сохранены оба источника и пометка конфликта.

Запрос о пяти почтовых адресах с расширением до пятнадцати зафиксирован в backlog. GitHub Pages не используется как почтовый сервер. Не создавать DNS-записи, почтовые ящики и CNAME этой итерацией.

## Финальный статус

В отчёте должны отдельно стоять:

- код создан / не создан;
- локальная сборка прошла / не прошла;
- тесты пройдены / не выполнены;
- изменения отправлены в ветку / не отправлены;
- Pages опубликован / не опубликован;
- фактический URL или точный оставшийся шаг.

Не заменять эту проверку фразой «готово, всё должно работать».

Эти вопросы не превращать в длинные предупреждения на утверждённой главной и не использовать как повод отказать в прототипе.

## Порядок точечных правок после v1

1. Сначала сверить главный экран, карточки и мобильную компоновку.
2. Затем уточнить тексты внутренних страниц и реальные контакты.
3. После этого подготовить портфолио и заменить недостаточные исходники.
4. Отдельной задачей подключить реальную отправку, выбранный домен, почту и производственные настройки.

Каждая правка — отдельный запрос с указанием страницы/блока. Не менять сразу всю концепцию после замечания к одному элементу.
